Job Status Subscriptions

A job status subscription lets a client hold a connection open to slurmctld and be told when job attributes change, instead of polling squeue or slurmrestd and diffing the results. The client describes what it cares about once; the controller then streams a snapshot of the matching jobs followed by updates as those jobs change.

This page describes the model and the reasoning behind it. It is aimed at someone maintaining or extending the implementation in src/slurmctld/job_subs.c.

The model

A client subscribes with a query, which has two parts:

  • a filter, the predicate deciding which jobs the query is about; and
  • an emit set, the attributes whose changes the client wants to hear about.

The controller answers with a server-assigned query id and then sends three kinds of message:

MessageSent whenPayload
MESSAGE_JOB_SNAPSHOT A job starts matching the filter, including at initial subscribe and on reconnect Job id and the current value of every attribute in the emit set
MESSAGE_JOB_UPDATE An attribute in the emit set changes on a job already matching Job id and only the attributes that changed
MESSAGE_JOB_DELETE A job stops matching the filter, including when it is purged Job id

An update is only sent when a value genuinely differs from what the client was last told, so a client can treat every update as real news. This falls out of how changes are recorded rather than from any per-client bookkeeping; see tracking changes below.

Filter attributes and emit attributes

Any tracked attribute may appear in a query's emit set. Only a smaller, explicitly enumerated set may be referenced by a filter. Today that set is job id alone.

Job id never changes over a job's lifetime, so a job-id filter only has to be evaluated once per job. The machinery is deliberately not written that way: filter attributes expected later — partition, account, QOS — are mutable, and a job can move in and out of a query's scope as they change. The implementation therefore re-evaluates a query's predicate whenever an attribute its filter references has changed, which is simply a no-op in the job id case.

Job state is deliberately not filterable. State is the highest-churn field in the system, and allowing filters on it would put every state transition on the membership-evaluation path. A client wanting "my pending jobs" subscribes to the jobs it owns and filters state itself from the update stream.

Tracking changes

Each tracked attribute has a bit in a per-job dirty mask. A job carrying any dirty bit is queued on a global modified-jobs list, so notification work never requires scanning the job list.

Dirty bits are set by per-attribute setters, which compare the new value against the current one and mark the attribute only on a real change. The underlying fields in job_record_t are const-qualified so that a direct assignment fails to compile: whether every mutation site is instrumented is answered by the compiler rather than by grep. Code that materializes a job record outside the controller's mutation path — unpacking saved state, rebuilding a record from accounting data — uses the job_record_init_* macros instead, which write the field without recording a change.

Because a dirty bit means the value actually changed, any query whose emit set includes that attribute is guaranteed to have something new to say. That is what makes the "only send real changes" guarantee free of per-query "last sent" state.

The flush pass

Notifications are not emitted as attributes change. A single RPC handler or scheduling cycle may touch several attributes on several jobs, and clients should see that batch only once it is complete and consistent. The flush pass therefore runs at the release of the job write lock, which marks exactly that boundary regardless of which subsystem made the change.

For each job on the modified-jobs list:

  1. Candidate queries are collected from a reverse index mapping each attribute to the queries whose filter references it, so only queries that care about something that actually changed are re-evaluated. Firehose queries (below) match unconditionally and are considered for every job.
  2. Each candidate's predicate is re-run. A job that has started matching joins the query's membership list and is sent a snapshot; one that has stopped matching leaves the list and is sent a delete. No change in the predicate's truth value means no message.
  3. Every remaining member whose emit set intersects the dirty bits is sent an update carrying just the changed attributes. A query that received a snapshot in this same pass is skipped, since the snapshot already carries current values.
  4. The job's dirty mask is cleared.

Job creation and purge

A new job is treated as having every filter attribute dirty, so the next flush evaluates each query against it and snapshots the matches through the ordinary path rather than a special case.

When a job is purged, its members are sent a final update for any dirty emit attributes that have not yet flushed, then the delete. In practice completion values were already flushed when the completing RPC released the job write lock, and the purge — typically MinJobAge later — sends only the delete. Either way a client sees a job's final state before it sees the job disappear.

A requeued job keeps its job id, so requeue is an ordinary state change rather than a delete followed by a snapshot.

Reconnect and timeout

A query lives in the controller, not in the connection, so a client that loses its connection can reconnect and present the query id it was given. The query is re-bound to the new connection and the client is sent a fresh snapshot of every job the query currently matches.

That snapshot — rather than a replay log — is what makes the client whole, and it is also the answer to a slow client. Since nothing has to be preserved for a client that is not reading, a client whose outbound queue grows without bound is simply disconnected; when it comes back it is handed correct current state. There is no need for the controller to choose between unbounded memory and silently dropping messages.

A query whose client does not return within SubscriptionTimeout seconds (default 120) is discarded by a periodic sweep. Reattaching to an id that has expired, never existed, or belongs to another user fails with Unknown or expired job subscription query id.

Delivery

The flush pass runs with the job write lock held, so it only appends messages to a per-connection queue. A separate thread per connection performs the blocking sends. A client that stops reading stalls only its own delivery thread and never the controller.

Authorization

Subscriptions are authenticated like every other Slurm RPC. An ordinary subscription only matches jobs owned by the subscribing user; privilege is resolved once when the subscription is created, since job ownership does not change.

Visibility is enforced inside the filter predicate rather than as a screen on outgoing messages. A job the client may not see never joins the query's membership list, so it produces no snapshot, no update, and no delete — the last of which would otherwise reveal that a job existed and finished.

The firehose

A cluster in which every interested tool holds its own subscription makes the controller pay for all of them. The intended remedy is a sidecar daemon that mirrors complete job state once and answers its own downstream clients.

For that, a subscription can be opened as a firehose: it matches every job unconditionally and its emit set is every tracked attribute. The emit set is derived from the attribute enumeration rather than listed out, so a newly tracked attribute joins the firehose automatically — which is what keeps such a mirror complete as Slurm grows. Because it crosses uid boundaries, a firehose may only be opened by SlurmUser or root.

Adding a tracked attribute

  1. Add an entry at the end of job_subs_attr_t in src/common/job_record.h, before JOB_SUBS_ATTR_COUNT. The order is wire protocol; existing entries must not be reordered.
  2. Const-qualify the field in job_record_t and add a setter, then let the compiler find the assignments that need converting.
  3. Pack and unpack the new field, under its mask bit, in the subscription event message.
  4. Add it to the filterable set only if a filter should be able to reference it, remembering that a mutable filter attribute puts every change to it on the membership-evaluation path.
